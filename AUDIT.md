# WaveQ codebase audit

Read-only audit. No source files were modified. Every line reference was verified against the file
as it exists on disk at audit time.

**Confidence notes — things I could NOT confirm without running the app on a device.** These are
marked `[UNVERIFIED]` in the table and I have deliberately not guessed at the outcome:

- `compileSdk`/`targetSdk` are **37**, which is past my knowledge horizon. All claims about platform
  enforcement (foreground-service type checks, background activity launch, full-screen-intent
  behaviour, DND volume restrictions) are based on documented Android 13/14 behaviour and must be
  re-verified on the actual target API level.
- Whether GMS Nearby delivers `PayloadCallback`/`ConnectionLifecycleCallback` on the main thread.
  It does by default (no `Executor` is supplied anywhere), but this drives several "main thread"
  findings below and is worth confirming with StrictMode or a systrace.
- The real encoded size of a 15-second AAC clip vs. the Nearby BYTES ceiling, and the exact failure
  mode when it is exceeded.
- Actual measured contrast ratios in dark mode (I reasoned from the hex values, I did not measure).

| 1 | `mesh/MeshManager.kt:283-287` | Remote-controlled path traversal. `payload.audioFileName` comes straight off the wire and is passed to `File(cacheDir, name)` then `writeBytes()` with no sanitisation. | 2 | `mesh/MeshManager.kt:281` via `mesh/NearbyTransport.kt:96-102` | Unguarded parse of an attacker-controlled payload. | 3 | `mesh/MeshSerialization.kt:48-49` | `payloadLen` is read from the wire and used directly as `ByteArray(payloadLen)` before any sanity check. | 4 | `mesh/SosBeaconService.kt:87` with `:62-86` | `START_STICKY` + no null-intent guard. | 6 | `alerts/SirenPlayer.kt:52-93` | No synchronisation on shared mutable state reached from at least three threads: `CriticalAlertTrigger`'s `Dispatchers.Default` scope, the Activity main thread (both buttons), and the auto-stop coroutine. ## Verified as correct (spot-checked, no action needed)

- **Hop count is incremented exactly once per hop and never on replay.** `MeshManager.kt:123` and `:232` increment on receive-then-relay; the incremented envelope is what gets stored (`:125`, `:234`), and `onPeerConnected` (`:260`) resends those stored bytes verbatim. Self-originated envelopes are stored at hop 0 (`:185`, `:212`), which is correct.
- **Fresh random IV per message.** `ChannelCrypto.kt:58` generates 12 bytes from `SecureRandom` on every encrypt; no IV reuse path exists.
- **No secrets in logs.** All 11 `Log` call sites were reviewed — none prints a passphrase, key, plaintext, or payload. The only sensitive-adjacent value is the role name at `MeshManager.kt:143`.
- **SOS and public FLOOD_ALERTs never touch encryption.** `sendSosBeacon` (`MeshManager.kt:196-216`) builds the envelope directly with `isEncrypted = false` and bypasses `ChannelRepository`/`ChannelCrypto` entirely; the SOS receive path (`:218`) does the same. FLOOD_ALERT rides the City-Wide channel, which is created with `isEncrypted = false` (`ChannelRepository.kt:57-70`).
- **Receiving is never role-gated.** The role check exists only in `sendMessage` (`MeshManager.kt:140`); relay, decrypt and SOS paths have none, and no receive path filters on role.
- **Self-siren suppression works.** `CriticalAlertTrigger.kt:33` drops `isMine` messages, and `isMine` is set both by the local echo and by `senderId == myDeviceId` (`MeshManager.kt:299`), so it holds even for a self-broadcast that loops back through the mesh.
- **Room is never touched on the main thread.** All DAO methods are `suspend`, so Room dispatches them to its own executor.
- **Theming migration is complete.** A full-tree grep for the 36 raw colour vals returns nothing outside `Color.kt`/`Theme.kt`/`AppExtraColors.kt` and the intentionally exempt `CriticalAlertActivity`.
- **SOS sequence overflow is not a real risk.** At one increment per 30 s, `Int.MAX_VALUE` is ~2,000 years. **Beacon id collision** is likewise negligible (random UUIDv4) — the real risk there is deliberate spoofing, finding #16.

## Needs a decision from you, not a code fix

1. **Unauthenticated mesh.** Findings #16, #17 and the whole malicious-peer class are not bugs in the implementation — they follow from the deliberate choice to auto-accept connections and leave SOS/public traffic unsigned so that any device can relay for any other. Signing beacons with a per-device key (published on first contact, trust-on-first-use) would close spoofing but adds key distribution to a system whose selling point is that it works with no infrastructure. Your call which property matters more.
2. **Passphrase-only channel join vs. offline cracking.** The deterministic salt (`ChannelCrypto.kt:37`) and the plaintext channelId (#15) both exist so a device can rejoin a family channel from the passphrase alone, with no invite code. That is a real usability requirement and a real crypto weakness. Fixing #15 is cheap; removing the deterministic salt is not, without introducing an invite/QR exchange.
3. **Where should alert dispatch live (#5).** Moving collectors to process scope fixes the dead alert path but means the app reacts to mesh traffic with no UI on screen, holding the radio and CPU in the background. That is a battery and user-expectation trade-off, and probably wants a foreground service of its own rather than a bare process-scoped coroutine.
4. **Should SOS survive process death at all (#4).** The current `START_STICKY` behaviour is dangerous, but the alternative — an SOS that silently dies when the OS kills the app — is also bad. If it should survive, the active beacon needs to be persisted and restored deliberately, with an explicit user-visible "SOS resumed" state.
5. **Voice notes: fix or remove (#12, #31).** They are half-built — recordable and sendable but not playable, and at the size ceiling. Either finish the feature (file payloads plus a player) or drop the mic button; leaving it as-is is worse than either.
6. **Client-side role gate.** Already flagged in-code at `SessionManager.kt:29-38`. The gate is enforced correctly and fails closed, but it is cosmetic against anyone willing to modify the app. Nothing to fix until there is a backend to trust.
7. **`securityCrypto` alpha dependency (#52).** Pin, migrate, or accept — worth deciding before this ships rather than at the next dependency bump.
