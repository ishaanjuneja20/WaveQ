# WaveQ post-merge audit (AUDIT2)

Read-only audit of the merged tree. **No source file was modified.** Every line reference was
checked against the file as it exists on disk at audit time.

Scope: the whole codebase, with extra weight on the seams named in the brief — `data/`, `model/`,
`ui/components/AnalyticsCharts.kt`, `ui/components/EvacuationCard.kt`,
`ui/screens/EvacuationMapScreen.kt`, and the four files rewired to host them (`AppNavigation.kt`,
`MeshViewModel.kt`, `OperatorScreens.kt`, `ReportDisasterSheet.kt`).

## What I could not confirm without running the app

These are marked `[UNVERIFIED]` in the table and I have not guessed at the outcome:

- `compileSdk`/`targetSdk` are **37**, past my knowledge horizon. Every claim about platform
  enforcement (foreground-service type checks, background activity launch, full-screen-intent
  gating, DND volume policy, package-visibility filtering) is reasoned from documented Android
  13/14/15 behaviour and must be re-checked on the real target level.
- **The tree has never been compiled** (`MERGE_NOTES.md` says so explicitly). I found no
  unresolved symbol, no signature mismatch and no ambiguous star-import collision by inspection,
  but I did not run `assembleDebug`. Two things are worth watching on the first build: the
  duplicate `import kotlinx.coroutines.launch` in `AppNavigation.kt` (finding 51) and the
  deprecated no-arg `fallbackToDestructiveMigration()` in `WaveQDatabase.kt` (finding 38).
- Whether GMS Nearby delivers `PayloadCallback`/`ConnectionLifecycleCallback` on the main thread.
  It does by default (no `Executor` is supplied anywhere), which drives several "main thread"
  findings.
- Exact osmdroid 6.1.20 internals: whether `GpsMyLocationProvider.startLocationProvider` swallows
  the `SecurityException` from `requestLocationUpdates`, and exactly what `MapView.onResume()`
  does. The *observable* consequences I report (finding 12, 13) follow from this app's own code
  regardless of which way those go.
- Real encoded size of a 15 s AAC clip against the Nearby BYTES ceiling.
- Measured contrast ratios in dark mode (reasoned from hex values, not measured).

## Needs a decision from you, not a code fix

1. **Should `SosBeaconService` start the transport at all?** Right now the mesh only starts when the
   user visits Mesh Channels (`MeshChannelsScreen.kt:56-58`) or when the SOS service starts it. A user
   who has never opened that screen has an SOS button that broadcasts into nothing, and the honest
   notification correctly says so. Options: start the mesh at app launch (battery cost, radio always
   on), start it on first Home visit, or keep it opt-in and put the "mesh is off" state on Home rather
   than only inside the SOS screen. Findings 1 and 2 make this urgent — today the failure is silent.

2. **Unauthenticated mesh.** Findings 3, 5, 23, 24 and the whole malicious-peer class follow from the
   deliberate choice to auto-accept connections and leave SOS/public traffic unsigned so any device can
   relay for any other. Findings 3, 4 and 5 are ordinary bugs and should be fixed regardless; 23 and 24
   are the design question. Trust-on-first-use device signing would close spoofing but adds key
   distribution to a system whose selling point is needing no infrastructure. Unchanged from AUDIT.md.

3. **Passphrase-only channel join vs. offline cracking** (finding 25). The deterministic salt and the
   plaintext channelId both exist so a device can rejoin a family channel from the passphrase alone.
   Fixing the channelId derivation is cheap; removing the deterministic salt is not, without an
   invite/QR exchange. Unchanged from AUDIT.md.

4. **Where alert dispatch lives.** AUDIT.md #5 (alerts dead when no Activity exists) is **fixed** by
   `MeshAlertDispatcher` for the case where the process is alive. Surviving full process death still
   needs a foreground service that owns the mesh — with the battery and user-expectation cost that
   implies. The `TODO(design-decision-3)` in `MeshAlertDispatcher.kt:23-28` states this correctly.

5. **Should SOS survive process death?** AUDIT.md #4 is **fixed** — the null-intent guard and
   `START_NOT_STICKY` remove the phantom-SOS risk. The cost, documented at `SosBeaconService.kt:56-60`,
   is that an OS-killed SOS stays dead. If it should survive, the active beacon needs to be persisted
   and restored deliberately with a visible "SOS resumed" state.

6. **Voice notes: fix or remove** (findings 26, 27, 50, 51). Recordable and sendable, not playable, at
   the payload size ceiling, and — via finding 1 — the reason a denied microphone kills the mesh.
   Either finish it (file payloads plus a player) or drop the mic button. Leaving it is worse than
   either. This one now has a safety consequence, not just a completeness one.

7. **What the incident pipeline is actually for.** The merge built persistence (finding 18 shows the
   read half is missing), relay, and a sync worker with no backend (finding 19). Decide whether an
   incident is: a local record only; a mesh-relayed observation other citizens see; or a report to
   authorities. Right now the UI claims all three and delivers the first two. The copy must match
   whichever you pick before this ships.

8. **Shelter and route data** (`model/SafeZone.kt:8`, `EvacuationMapScreen.kt:74`). A three-entry
   hardcoded Bijnor demo set and a straight-line route that may cross a river or a ridge. Both are
   documented as TODOs. Either ship them behind an explicit "demo data" label or get an authority feed
   and a real routing engine before the evacuation screen is reachable in a release build.

9. **Client-side role gate** (`SessionManager.kt:29-38`). Enforced correctly and fails closed, but
   cosmetic against anyone willing to modify the app. Nothing to fix until there is a backend to trust.
   Unchanged from AUDIT.md.

10. **`securityCrypto` alpha dependency** (`libs.versions.toml:13`, `1.1.0-alpha07`). An alpha crypto
    dependency guarding channel keys, on a deprecation path with no migration plan. Pin, migrate, or
    accept — decide before shipping. Unchanged from AUDIT.md. Same for
    `android.disallowKotlinSourceSets=false` (`gradle.properties:23`), an experimental AGP escape hatch.

### Merge seams the brief asked about — verified as correct

- **Two Room databases coexisting.** No conflict. `waveq_incidents`, `waveq_mesh_store.db` and
  `waveq_prediction_cache.db` are three distinct files with three distinct `RoomDatabase` subclasses.
  Each is effectively a singleton (`WaveQDatabase` via double-checked locking; `MessageStore` and
  `OpenMeteoDataSource` via field initialisers on objects that `MeshSession.init`/`RiskRepository.init`
  create exactly once under `@Synchronized`). No shared migration path, no duplicate instances, no
  cross-database transactions. Their *policies* are inconsistent (finding 38) but their lifetimes are
  not in conflict. Every DAO method in all three is `suspend` or returns `Flow`, so Room dispatches off
  the main thread — no main-thread queries anywhere, and `allowMainThreadQueries` is never called.
- **`IncidentRepository` constructed in a composable with `remember`.** Correct and leak-free.
  `remember(context)` is keyed on a value stable for that destination, so it is created once, not per
  recomposition. It captures `context.applicationContext`, never an Activity, and its `dao` comes from
  the process-wide DB singleton, so multiple instances would be harmless anyway. The real bug in this
  flow is the coroutine scope (finding 17), not the repository.
- **Hop count.** Incremented exactly once per hop and never on replay. `MeshManager.kt:142` and `:308`
  increment on receive-then-relay, the incremented envelope is what gets stored (`:144`, `:310`), and
  `onPeerConnected` (`:337`) resends the stored bytes verbatim. Self-originated envelopes are stored at
  hop 0 (`:218`, `:287`). `tryDecryptAndEmit` receives the *original* envelope, so `MeshMessage.hopCount`
  correctly reports hops travelled at the moment of receipt.
- **Fresh random IV per message.** `ChannelCrypto.kt:58` draws 12 bytes from `SecureRandom` on every
  encrypt. No reuse path exists.
- **No secrets in logs, disk or crash reports.** All `Log` call sites reviewed — none prints a
  passphrase, key, plaintext or payload. Only the derived key is persisted (in
  `EncryptedSharedPreferences`), never the passphrase. Decrypt failure fails closed and silently for
  the wrong-key case (finding 60 covers the other JCE exceptions).
- **SOS beacons, FLOOD_ALERTs and RISK_UPDATEs never go through encryption.** `sendSosBeacon`
  (`MeshManager.kt:271-292`) builds the envelope directly with `isEncrypted = false` and bypasses
  `ChannelRepository`/`ChannelCrypto` entirely; the SOS receive path does the same. FLOOD_ALERT and
  RISK_UPDATE ride the City-Wide channel, created with `isEncrypted = false`
  (`ChannelRepository.kt:57-70`), and `sendMessageTo` explicitly refuses encrypted channels
  (`MeshManager.kt:244-247`).
- **Role gating is enforced in `MeshManager`, not only in the UI.** `MeshManager.kt:171-177` blocks a
  `FLOOD_ALERT` unless the session role is OPERATOR/ADMIN, regardless of caller, and fails closed on a
  null role. Receiving, relaying, decrypting and SOS are correctly *not* role-gated. Every operator
  route is additionally gated at the nav graph (`RequireRole`), and `content()` is never invoked for an
  unauthorised role, so no operator screen renders even for a frame. There are no `<intent-filter>`
  deep links into the nav graph — `MainActivity` is LAUNCHER-only and `CriticalAlertActivity` is
  `exported="false"` — so there is no unguarded route in. The merged `EVACUATION` route is ungated by
  design (it is citizen-facing). The pre-DataStore window is covered by finding 71.
- **Self-siren suppression.** `CriticalAlertTrigger.kt:33` drops `isMine` messages, and `isMine` is set
  both by the local echo and by `senderId == myDeviceId` (`MeshManager.kt:376`), so it holds for a
  self-broadcast that loops back through the mesh. `MeshAlertDispatcher.kt:66` independently drops
  own-device SOS beacons, and `CriticalAlertTrigger.kt:126` suppresses everything while this device's
  own SOS is active.
- **Relayed RISK_UPDATE staleness and distance rules.** `RiskRepository.onRiskUpdateReceived`
  (`:479-531`) refuses to adopt — and therefore refuses to siren — unless the update is within 25 km
  *and* its source data is under 3 h old *and* it is fresher than what this device holds. An
  unverifiable distance (no GPS fix) is treated as failing, not passing. Confidence is recomputed from
  the original `dataFetchedAt` in `RiskSerialization.fromJson` (`:197`), so relaying cannot launder a
  stale assessment into a fresh-looking one. The sender's transmitted confidence is explicitly not
  trusted (`:174`). This is all correct.
- **Risk-engine division and NaN.** Every normalisation guards its divisor:
  `weightedScore` returns 0 when `availableWeight <= 0`; `computeDischargeTrend` rejects `mean <= 0.0`;
  `computeSoilSaturation` and `computeTerrainAmplification` divide by non-zero constants;
  `RainfallThresholdCurve` has no zero threshold; `confidenceFor` guards `totalWeight > 0`;
  `DischargeChart` guards `span`. No divide-by-zero or NaN path found in the engine. The engine's real
  problem is finding 7 (renormalisation letting one indicator reach CRITICAL alone), not arithmetic.
- **"No data" is not reported as LOW.** `recomputeDevice` (`:306-322`) returns an explicit status
  message rather than a zero score when all inputs are missing, `RiskGaugeEmpty` renders "--" rather
  than a LOW gauge, and `confidenceExplanation` degrades honestly with age. The one exception is
  `RiskRepository.currentSeverity()` (`:589`), which returns `Severity.LOW` when `device == null` — but
  it has no callers, so nothing acts on it. Worth deleting before something does.
- **Network calls are off the main thread.** Every `OpenMeteoDataSource` and `PlaceSearch` method wraps
  its Retrofit call in `withContext(Dispatchers.IO)`, and every HTTP/parse failure is caught and
  degraded to cache rather than propagated. Timeouts are short and deliberate.
- **Theming migration.** A full-tree grep for the 36 raw colour vals returns only
  `CriticalAlertActivity` (intentionally exempt — documented at `Color.kt:10-16`), two `BrandRed`/
  `OnLightChip` uses in `SosScreen`'s white-on-red warning card (deliberate, that card is white in both
  themes), and one hardcoded hex in `MapPlaceholder` (finding 47). The three merged UI files —
  `AnalyticsCharts.kt`, `EvacuationCard.kt`, `EvacuationMapScreen.kt` — read `MaterialTheme.colorScheme`
  and `appExtraColors` throughout, as `MERGE_NOTES.md` claims.
- **`MeshViewModel` initialisation order.** `init { MeshSession.init(application) }` is declared at
  line 39, before the `val channelRepository = MeshSession.channelRepository` property initialisers at
  lines 53-56. Kotlin runs `init` blocks and property initialisers in declaration order, so the
  `lateinit` fields are populated before they are read. This is load-bearing and easy to break with a
  reorder — worth a comment in the file.
